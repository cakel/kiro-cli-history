## 진행한 작업

### GitHub Actions release.yml 신설

- 트리거: `v*` 태그 push (패턴: `v0.1.0-cakel.N`)
- 동작:
  1. `_version.py`의 `VERSION` 상수를 태그명으로 자동 교체 (sed)
  2. `main`에 `chore: bump VERSION to <tag>` 커밋 push
  3. GitHub Release 자동 생성 (`generate_release_notes: true`, `make_latest: true`)

### 태그 갱신 방식 결정 (C 방식)

수정 후 같은 태그를 갱신할 경우:
```bash
git tag -d v0.1.0-cakel.N
git push origin :refs/tags/v0.1.0-cakel.N
git tag v0.1.0-cakel.N
git push origin v0.1.0-cakel.N
```
- GitHub Release는 태그 삭제 시 함께 삭제됨
- 태그 재push 시 워크플로우 재트리거 → Release 재생성
- 혼자 관리 + 외부 링크 없으므로 링크 깨짐 단점 없음

### 버전 정책

- `v0.1.0-cakel.N` 형식: 이 fork에서 관리 (자동화)
- `v0.1.0` 형식 upstream 버전 변경: 수동으로 직접 처리

## cakel.5 수동 정리

release.yml이 cakel.5 태그 push 이후 main에 들어와서 첫 태그는 워크플로우 미트리거.
수동으로 처리:
- `gh release edit --draft=false --latest` 로 published + Latest 설정
- lightweight tag → annotated tag 재생성 (C 방식)
- Release 노트 한국어 → 영문 교체

cakel.6부터 release.yml 자동 동작 예정.

## 태그 갱신 시 주의 (C 방식)

```bash
git tag -d v0.1.0-cakel.N
git push origin :refs/tags/v0.1.0-cakel.N
git tag -a v0.1.0-cakel.N <commit> -m "메시지"
git push origin v0.1.0-cakel.N
```
- 태그 삭제 시 GitHub Release도 삭제됨
- 재push 시 release.yml 트리거 → Release 자동 재생성 (draft=false, make_latest=true)
- Draft로 남을 경우: `gh release edit v0.1.0-cakel.N --draft=false --latest`

## _version.py 동작 정리

| 변수 | 값 | 용도 |
|------|-----|------|
| `VERSION` | `"v0.1.0-cakel.N"` | 하드코딩 fallback. 태그 push 시 자동 업데이트 |
| `_BUILT_VERSION` | `""` → install 시 git 태그로 교체 | install.sh/ps1이 주입 |
| `_BUILT_HASH` | `""` → install 시 git hash로 교체 | install.sh/ps1이 주입 |

런타임 우선순위: `_BUILT_VERSION+_BUILT_HASH` → `_BUILT_VERSION` → git 직접 읽기 (dev mode) → `VERSION` fallback
